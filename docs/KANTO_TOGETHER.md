# Kanto Together in RetroHub

Kanto Together is a two-player co-op ROM hack of Pokemon FireRed made by a friend of the user. RetroHub does **not** ship it: it is installed from the user's own zip (`KantoTogether-ROM-*.zip`, or an extracted `KantoTogether-ROM` folder) found in the ROM folders. The zip is only ever read.

Credit: the hack, its Node launcher/relay protocol and `coop.lua` are the friend's work. Bundled third party code inside the package: mGBA (MPL 2.0), Node.js (MIT), `ws` (MIT); see `LICENSES.txt` in the installed package (Open licences button in the How to play sheet). The patch derives from pret/pokefirered and contains no Nintendo ROM.

## Flow

1. **Library**: `kanto::find_packages` (src/common/kanto.cpp) walks the ROM folders (names containing "kanto" only) and `kt_scan_append` adds one card, `gba:kanto-together`, "Kanto Together (FireRed co-op)", catalog id `kanto` (2 players, online, FireRed cover art). The package can be the zip or an already extracted `KantoTogether-ROM` folder. Both are the same build (keyed on `patch.json` patchSha1 + built), so switching between them does not reinstall; when both exist, the folder is preferred.
2. **First Play = Install**: `kanto::Prep` (worker thread) copies the package into `<data>\apps\KantoTogether` (progress; skips the package's own `rom\` and `saves\`; rejects unsafe paths), picks the user's FireRed from the library by SHA-1 (`41cb23d8dccc8ebd7c649cd8fbb58eeace6e2fdc`, USA v1.0; clear messages for "no FireRed" / "wrong revision") and runs the package's `apply-patch.mjs --rom <that file>` hidden to build `rom\KantoTogether.gba` (verified against the manifest's target SHA-1). Play then points to the Online page.
3. **Rooms**: select Kanto Together (exactly 2 players). The host's Launch sends the usual `launch` message and starts `node app\coop-launch.mjs host ...` **hidden** (`CREATE_NO_WINDOW`, piped stdin/stdout, kill-on-close job; mGBA's game window shows normally). The ROOM CODE is read from the output and sent to the guest with `{"kind":"np_kt","code":"..","launch":N}`; the guest's RetroHub runs `join CODE` by itself. A new code (host restarted, idle refresh) is forwarded again and the guest's RetroHub types `code NEWCODE` into the running launcher. Sound is on (`--unmute`). Closing the game ends the session.
4. **Panels** (room page): connection status (starting / waiting / partner connected / reconnecting / partner away / failed) and a Trade panel: slot 1-6 sends `trade N`, the partner's offer is parsed from the output, Confirm/Cancel send `confirm`/`cancel`.
5. **Saves**: per role. The vault (`hub::saves::battery_dir("gba", "gba:kanto-together")`) keeps `KantoTogether.host.sav`, `KantoTogether.guest.sav` and the role's `coop-trade-<role>.journal`; mGBA runs in a staged folder per role (`<data>\netplay\kanto\saves_host|saves_guest`, 8.3 short path if non-ASCII). `kanto::stage_saves` copies in (newest wins, a crash-leftover journal survives), `flush_saves` copies back after exit (journal mirrored, then removed from the staged folder). A legacy `KantoTogether.sav` seeds the first role played and becomes `KantoTogether.sav.pre-roles`. Before start: `running_instance_block` (any package mGBA/Node or port 8788) and a `coop-launch --dry-run` preflight (exit 2/3 mapped to messages). The launcher runs with `--verbose`; `[launch]` lines are failures only when they match known fatal texts. The install marker is the package's patch.json patchSha1+built (zip and folder are the same build); `runtime\mgba\config.ini`/`qt.ini` are never overwritten on reinstall.
6. **Controllers**: RetroHub's `retro` pad profile is written into mGBA's `[gba.input.SDLC]` section (`src/common/kanto_pad.cpp`, `pad_bindings`) and rewritten when its hash changes. The first button term per control is used, and A/B are swapped to the GBA layout only for the default profile. 

## Network

The package connects to its relay only: `COOP_RELAY` env > first non-comment line of its `online-address.txt` > `wss://77.113.17.34/kanto-relay` (the maintainer's default; the shipped `online-address.txt` has no address). The relay only forwards game-state lines (position, party, trade messages); the bridge whitelists which line types may reach mGBA's Lua. RetroHub passes a free loopback port with `--lua-port` (the package default 8788 would clash). Overrides for tests: `RETROHUB_KT_RELAY` (becomes `COOP_RELAY`), `RETROHUB_KT_DESKTOP` (start everything on a named hidden desktop), `RETROHUB_KT_MUTE` / `RETRORUN_MUTE` (mute).

## Tests

- `hubkanto_test` (ctest): package detection, install, SHA-1, ROM pick, command lines, output parsing, saves.
- `kanto_live` (manual): installs from the zip into a scratch dir, builds the game, runs a local relay (`qa\kanto_local_relay.mjs`, 127.0.0.1) + host + guest on a hidden desktop, muted, and waits for both sides to report "Your partner is connected".
- `qa\kanto_shots.ps1`: headless screenshots (card, room status, trade panel, setup, how-to).

## Package versions, updates and start-up barriers (package built 2026-10-24T20:12Z, "sync barriers")

**What changed in the friend's package** (old a6c685b0..., built 08:38Z -> new 488ce08c..., built 20:12Z; target ROM sha1 b41b91db -> 48345f99): `coop.lua` gained start-up barriers (title screen, Oak's speech, naming, first bedroom frame: both games wait for each other, buttons paused, "Waiting for partner..." strip), a periodic world `HASH`/`RSYNC` check with `resync`, and the console commands `go`, `barrier on|off|status`, `keys`. The bridge whitelists the new lines `HASH RSYNC PH`, logs link RTT and has a `COOP_TEST_DELAY` test knob. The launcher has `--no-barriers`, writes `<saves>\coop-<role>.log` (5 MB max) and adds Xbox pad bindings to mGBA's `config.ini` (`mgba-controls.mjs`, portable mode only). `patch.json`, the `.bps`, `QUICK-START.txt` and `runtime\mgba\config.ini` changed; the `.cmd` files, `online-address.txt`, `package.json` and node/ws did not. Both players must run the same build: with an older partner the script logs "older version without start-up barriers" and the old behaviour returns.

**The CoopLayer developer package** has the same `coop.lua`, bridge and launcher (byte-identical to the game package) plus the MIT-licensed relay, ROM-side C sources, tests and an integration guide. It is for embedding the layer into another emulator frontend, not an API for RetroHub: RetroHub already runs the layer the way the guide recommends (mGBA with Lua plus the Node bridge as a sidecar over loopback, driven through the launcher's stdin/stdout). The only machine-readable surface is the console text; the guide says the `SYNC:` lines are "text for humans, not a stable API", so RetroHub matches them loosely (`kanto::feed_line`) and treats each as optional. Nothing from CoopLayer is shipped or vendored (its ROM-side patch is pret-derived and not MIT); `THIRD_PARTY.md` credits the author and licences.

**Seamless updates.** `find_packages` also looks at the top level of the user's Downloads folder (kanto-named zips/folders only), and `pick_package` takes the newest `patch.json` `built`. The install marker is the build id (`patchSha1@built`), so a newer package reinstalls over `<data>\apps\KantoTogether` automatically (no manual deleting). The patched ROM is rebuilt from the user's FireRed when its sha1 differs from the new target. Saves are untouched: they live in the vault (`KantoTogether.host.sav` / `.guest.sav` plus the role's trade journal) and are staged into `netplay\kanto\saves_<role>`, never in the package's own `saves\` (which RetroHub does not read or write). A newer package that shows up after a library rescan is picked up the next time the room page is shown (`check_package_update`). The install's mGBA `config.ini`/`qt.ini` are kept on reinstall (RetroHub writes the pad bindings into them).

**Version check in rooms.** Once the install is ready each RetroHub broadcasts `{"kind":"np_kt_ver","id":<patchSha1>,"built":..,"bar":0|1}` (again whenever the member list changes). The host's Launch is blocked with e.g. "Mickey has an older Kanto Together package - they need to update" (or "has a newer ... package - you need to update"). The host's `np_kt` code message carries `pkg`; a guest whose build differs refuses to join and sends `np_kt_fail` with reason `pkg_old`, `pkg_new` or `pkg_diff`. A partner on an older RetroHub (no `np_kt_ver`) cannot be checked and is allowed.

**Barriers in the UI.** The status panel shows "Waiting for your partner (you are at: ...)" with a Skip waiting button (`go`), a hint when the partner's package has no barriers, and a note when the script switched them off (a game build it does not know). For support, ask for `saves\coop-<role>.log` from the staged folder and RetroHub's `userdata\logs\kanto-<date>.log`.

**Testing.** `hubkanto_test` covers version parsing and comparison, block texts, `go` and barrier line parsing. `kanto_live` (manual; hidden desktop, muted, loopback relay only) accepts `KT_LIVE_GUEST_DELAY=<s>` (the host waits at the title screen: barrier lines) and `KT_LIVE_GUEST_PKG=<zip>` (mixed-version session: legacy-peer line).
