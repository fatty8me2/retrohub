# Owner dashboard, blacklist and approval mode

The owner account (the Worker's `ADMIN_UID`) gets an **Admin** page in RetroHub. Everyone else never sees it, and the Worker refuses every `admin_*` message from any other account, so hiding the page is a convenience, not the security.

## Who is the admin (server side)
- An admin message is honoured only on a socket that passed the normal friends hello **for the `ADMIN_UID` account with its stored secret** (`SHA-256(secret)` match, else close 4003). The `uid` in the URL and any `uid` / `admin` fields in a message body are never trusted: the hub answers from its own stored profile.
- A non-admin sending any `admin_*` type gets exactly what an unknown message type gets: no reply, no error, no log line. The welcome carries `admin:true` for the owner only.
- Admin calls are limited to 60 per minute (in memory) on top of the normal per-account message budget.
- The registry (Durable Object `AdminRegistry`, binding `ADMIN_REG`) has no public route; it only answers requests with the internal header, and its list/detail/ban/settings/seed routes also need the admin uid, which only the admin's own hub sends.

## What is stored (and what is not)
One row per account, hard capped: uid, display name, username, created, first/last seen, PC estimate (most simultaneous sockets seen), status (`ok | pending | banned | denied`) and who set it. **No IP address, message, file name or anything else new.** Test accounts (`qa-` names, `test:true`) are never stored or listed.

## Client -> server
| Message | Effect |
|---|---|
| `{type:"admin_list", q?, sort:"last"\|"first", order:"asc"\|"desc", status:"all"\|"pending"\|"banned"\|"ok", offset, limit<=50}` | page of accounts; the first call seeds the registry from the admin's own friend list (300 per step) |
| `{type:"admin_detail", uid}` | how they got onto your list (`auto`/`request`/`room`), friend names (<=30), first/last seen |
| `{type:"admin_ban"\|"admin_unban"\|"admin_approve"\|"admin_deny", uid}` | status change; replies `admin_result` |
| `{type:"admin_settings", set?:{approval?, vouch?, autofriend?}}` | read or change the switches |

Server -> client: `admin_list`, `admin_detail`, `admin_result`, `admin_settings`, `admin_pending` (push when a new account starts waiting).

## Ban / deny
The registry marks the uid and pushes the verdict to the account's hub, which closes its sockets (4010) and, over alarm steps of 25 (Workers Free allows 50 subrequests per invocation), removes its friends and cancels/declines its requests everywhere. The admin's own friend rows and requests for it go at once. The banned hub then answers every internal call with "no such account", its `link_auth` / `saves_auth` refuse (links, cloud saves), and the room server closes its seat at `ident` (4010). Hello gets `{error: "account-unavailable"}` and the socket is left open, so shipped clients do not retry in a loop. An unban pushes `ok` and closes the waiting socket (4011) so the client reconnects at once. A ban recorded for an uid that never registered sticks for when it does.

## Approval mode (default ON; accounts created before 2026-11-03 are grandfathered)
Turning it on records a cutoff. An account whose own `created` time is before the cutoff is grandfathered and untouched. A newer account is `pending`: the client shows only the lock screen (no offline play either, see "Locking the whole app"); friends, rooms, saves and links answer `pending-approval` ("Waiting for the owner to approve this account"; room seats close 4012). Approve/deny from the Pending view; approval wakes the waiting client (4011). Turning the mode off lets waiting accounts in on their next check (at most two minutes).
- **Vouch** (separate toggle, default OFF, needs approval mode): a waiting account that an approved account adds **by friend code** is approved; at most 5 per voucher.
- A spoofed test account is not a way around the gate: with approval on, test accounts are refused too (and invisible).

## Auto-friend toggle (default ON)
Off: new accounts are not added to the owner's friends (an account that connects while it is off is skipped for good). Existing friends are never touched.

## Safety rules (no existing account is ever locked out)
- An **error** never locks anybody out. If the registry cannot be reached at hello: an account with an `ok` verdict is welcomed; an account with no verdict that is older than 24 h is welcomed (nothing is cached, so it registers at its next hello); a brand-new account is held **only while approval mode is known to be on** (otherwise it is welcomed too, and the admin auto-link is retried later, never marked done). Only an explicit ban/deny, or a brand-new account under approval mode, is ever refused. An unreadable verdict counts as `ok`.
- **Seeding** never makes anybody pending: accounts seeded from the owner's friend list are `ok`, `by=seed`, creation time unknown until their own hello reports it. Seeding restarts when the owner's friend list grows or after 24 h.
- **Rollback.** Every stored verdict is ignored when the `ADMIN_REG` binding is absent (`gateLocal()` returns `ok`, `acctGate` skips the registry), so redeploying the previous code, or this code without the binding, lets everyone back in at once. Keep the `AdminRegistry` class exported and the `v8` migration in place: removing the class from the exports while the migration history still lists it makes `wrangler deploy` fail, and a `deleted_classes` migration would destroy the registry's stored data. Do not add a `deleted_classes` migration unless you mean to drop the bans and the account list.
- A **failed push** (ban, unban, approve, deny) is not lost: the row is kept `unapplied` (the dashboard shows "Not applied yet - retrying"), the registry retries from an alarm (1 min, then every 5 min), a banned hub re-checks the registry at least every 10 minutes (so a missed unban cannot stick), and every hello of an approved account checks in at least every 6 hours (so a missed ban lands, closing the account's other authenticated sockets).
- **Local QA servers.** Approval mode is ON by default, so a fresh test account is held pending and refused. Every local `wrangler dev` used for tests passes `--var REG_APPROVAL_DEFAULT:0 ALLOW_TEST_FLAG:1` (`qa/_localworker.ps1` and the qa scripts that start their own worker do); `qa/strict_rooms_e2e.mjs` shows the strict-rooms setup.
- **Test accounts.** The client's `test:true` flag and `qa-` names are honoured **only** where `ALLOW_TEST_FLAG=1` is set (local wrangler and the test suite; production never sets it). Without it they are ordinary accounts: auto-linked, listed, subject to approval. With it, test accounts are stored (flagged), count toward the caps, are hidden unless "Show test accounts" is on, and are still bound by bans and approval mode. Local online runs: start wrangler with `--var ALLOW_TEST_FLAG:1`.
- **Banned usernames stay reserved** for the banned account (nobody else can take a banned person's name or impersonate it).
- A vouched account cannot vouch (no chains); `admin_peek` returns at most 30 friend names.

## Caps (free tier)
20 000 account rows (past it new `ok` accounts are simply not tracked, never refused), 500 queued pending (past it still refused, not queued), 3 000 bans, 5 vouches per voucher, 50 rows per page, 4 x 300 seed rows per list call, 60 admin calls a minute. An approved account re-checks in with the registry at most every 6 hours (1-2 rows written), so the registry adds roughly one write per active account per 6 hours to the rows budget.

## Client
`src/net/admin_logic.h` (pure; `hubadmin_test`), `FriendsClient::is_admin()/admin_*()/access()`, `src/hub/page_admin.cpp`. Screenshot aids: `HUB_SHOT_ADMIN=1|pending|banned|detail|confirm|settings`, `HUB_SHOT_ACCESS=pending|unavailable|setup|setup-offline` (the whole-app lock screens, below).

## Locking the whole app (client side)
A banned, denied or not-yet-approved account is blocked from RetroHub entirely, not only from Play Online. Logic: `src/hub/lockout_logic.h` (pure; `hub_lockout_test`), glue and lock screen: `src/hub/lockout.cpp`.
- **What locks.** While the verdict is Pending or Unavailable (or a brand-new install has not yet heard Ok), `draw_frame` draws only a full-window lock screen: no library, Discover, saves, controllers, settings, party, admin, friends panel or toasts. Pending: "Waiting for approval", this account's name and friend code (so the owner can recognise it), Check again, Quit. Unavailable: "This account can't use RetroHub" with no detail, Check again (so an unbanned person unlocks without restarting) and Quit. A new install that has not reached the server: "Setting up RetroHub" for a few seconds, then "Connect to the internet to finish setting up" with Check again and Quit. All are pad-navigable. Check again calls `FriendsClient::reconnect_now()` (an access refusal otherwise slows reconnects to a minute).
- **No launch gets through.** `launch_blocked()` is asked first by `play_entry`, `play_entry_anim` (quick launch, `--play`, Add to desktop shortcuts, resume, hacks, challenges, party), `spawn`, `launch_external`, `launch_online`, `launch_online_3ds`, `launch_online_wiiu`, `gc_begin`, `gc_guest_prepare`, `kt_play`, `host_launch_selected`, `guest_apply_launch`, `enter_room`, `rejoin_room`, `fr_join_lobby` (invites, bell, `retrohub://join/`, `--join`), `dropin_start` and `spectate_start`. Command-line and protocol requests are dropped in `main.cpp` while locked.
- **A game already running is left alone.** The lock never pops up, focuses or closes anything. The game runs until it exits by itself; the lock is drawn in the hub window (behind the game) and any room is left quietly once the game has ended. The running game keeps its own quick menu.
- **The verdict is remembered** in `<data dir>\access.json` (verdict, account id, owner flag). A cached Pending/Unavailable locks at startup even offline and unlocks only when the server welcomes the account. A cache written for another account id is ignored.
- **Upgrade safety.** An install that already has an account (identity file) and no cache is treated as Ok until the server says otherwise; being offline never locks an existing friend. A brand-new install (no identity, no cache) stays locked until it receives its first Ok: the friends client registers at startup, so this is a second or two online. The moment the account is created a `"setup"` marker is written to access.json, so quitting or going offline before the first Ok does not unlock the next start (an upgrader has no access.json and is never marked).
- **The owner is never locked** (the welcome's admin flag is cached; a cached or live refusal is ignored for an owner account).
- **Silent sockets.** A refused account's socket is left open and silent by the server, so the client re-checks it with one hello every 3 minutes (never a loop); a hello that gets no answer for 30 s is treated as a dead socket and reconnected with the normal backoff. Armed deferred launches (a Kanto guest start, a room being prepared) are guarded or cancelled when the lock comes on.
- **Rooms and saves.** Every lobby seat (host, guest, spectator, drop-in) now sends an ident; with auto-friend off it carries `nopair:true` (proof of the account, no pairing), so the owner's `strict_rooms` switch ("Only approved accounts can join rooms", Admin page, default off; friends older than 1.31.11 cannot join rooms while it is on) works for everyone. A close 4013 / `ident-required` is shown as "This room needs a RetroHub account" and never retried; 4010 / 4012 are never retried either. A `server-busy` refusal never locks. A `/saves` 403 with a gate reason is a quiet "try later" (not a device limit, not corrupt data) and feeds the same verdict until the friends socket is welcomed.
- **Game-room sockets (runners).** With strict rooms the server wants an ident from every seat, game rooms and spectators included. `hubnet::Session` (n64run, retrorun, streamrun, the hub's own 3DS/GameCube forwarders) sends `{type:"ident",uid,secret,nopair:true}` after the welcome (proof only, no pairing). A runner gets the account through the inherited environment variable `RETROHUB_IDENT` (`<server>|<uid>|<secret>`, `src/net/ident_env.h`), which `spawn()` / `start_hidden()` set only around the `CreateProcess` of our own exes and clear again: never on a command line, never logged, and bound to one server (a runner pointed elsewhere sends nothing). Emulators (Dolphin, Cemu, Azahar, PCSX2) never get it. A 4014 / `server-busy` answer to the proof (the registry is down and the account is new) is temporary: "Server busy, try again shortly", retried with a growing backoff, never a lock. `qa/strict_rooms_e2e.mjs` runs this against a local worker. Not covered: the native Smash port (BattleShip repo) gets the variable but must read it itself.
- **Off** for headless runs, the QA room driver (`RETROHUB_AUTOTEST`) and fake-friends screenshots.
- **Limits.** This is a client-side lock: a modified client can skip it. The server is the real gate and refuses a banned or unapproved account every route; the lock only keeps honest installs from being used.
